# Quality Management System — Web Application (QMSWebapp)

> **For:** Mentor App Generator + Manual Implementation (ODC)  
> **Generated:** 2026-09-27  
> **App Type:** Web Application (ODC)  
> **Depends on:** QMSBackend (QMSDefectAPI REST API)  
> **Status:** Ready for Development  

---

## 1. Overview

QMSWebapp is the user-facing web application for the Quality Management System. It provides quality engineers, supervisors, and managers with a browser-based interface to view, create, update, and soft-delete manufacturing defect records. All data operations are performed exclusively through the QMSDefectAPI REST API exposed by the QMSBackend service — QMSWebapp has no direct database access and no local entities of its own.

The app demonstrates OutSystems' REST API consumption patterns, role-based access control, error resilience, and form-driven workflows.

---

## 2. App Type and Architecture

- **App type:** Web Application (ODC)
- **Data persistence:** No local entities — all data lives in QMSBackend
- **Database access:** No direct queries — all reads and writes go through REST API
- **Integration:** Consumes QMSDefectAPI via a REST client
- **Authentication:** Every outbound request must include header `X-API-Key` with the value of a Secret Setting named `QMSAPIKey`, configured per stage in the ODC Portal

**Key Principle:** QMSWebapp is a stateless consumer app. The backend (QMSBackend) is the single source of truth. QMSWebapp never caches data — it fetches fresh data on every screen load or user action.

## 4. REST Client Integration (Manual Configuration in ODC Studio)

**Critical:** The REST client cannot be auto-generated by Mentor. It must be manually configured after app generation.

### 4.1 Create the REST Client

1. In ODC Studio, go to **Integrations** (bottom panel)
2. Click **REST** → **Add REST Client**
3. Name: `QMSDefectAPI`
4. Base URL: Leave empty (will be built dynamically using `Settings.QMSBackendBaseURL`)
5. Add the **OnBeforeRequest callback:**
   - Purpose: Inject the `X-API-Key` header on every outbound request
   - Callback type: **Function** (returns modified request)
   - Pattern:
     ```
     OnBeforeRequest(Request):
       Request.Headers.Append(
         Name = "X-API-Key",
         Value = Settings.QMSAPIKey
       )
       Return Request
     ```
   - This ensures every API call includes authentication

### 4.2 Define Consumed Endpoints

Add these six server actions to the REST client (one per endpoint):

| Method | Path | Server Action Name | Purpose |
|---|---|---|---|
| GET | /defects | ListDefects | List defects (paginated, filterable) |
| GET | /defects/{DefectId} | GetDefectDetail | Get full defect detail |
| GET | /defects/{DefectId}/history | GetDefectHistory | Get defect history records |
| POST | /defects | CreateDefect | Create a new defect |
| PATCH | /defects/{DefectId} | UpdateDefectStatus | Update defect status and resolution |
| DELETE | /defects/{DefectId} | DeleteDefect | Soft-delete a defect |

### 5.3 Implementation Pattern

**UI-level enforcement:**
- Hide buttons, links, and screens from unauthorized roles using `If` blocks or conditional visibility
- Example: `If User_GetRoles().Contains("QualityManager") Then ... Else ... End If`

**Server-action-level enforcement (mandatory):**
- Every server action that modifies data (Create, Update, Delete) must check role authorization
- Raise a `Security Exception` if the user lacks the required role
- Example:
  ```
  If Not User_GetRoles().Contains("QualityManager") Then
    Raise Security_Exception("You do not have permission to update defect status")
  End If
  ```

**Unauthenticated users:**
- Are automatically redirected to the **Login** screen by ODC (built-in behavior)
- Session timeout defaults to 60 minutes; configure in ODC Portal if needed

- Hide the table

**Error state (API call fails):**
- Hide the table
- Display error banner: `"Unable to load defects. Please try again."`

#### 6.2.6 Server Action Pattern (ListDefects)

```
ListDefects(Status: Integer, ProductLine: Text, Page: Integer, PageSize: Integer):
  [Call REST client: GET /defects?Status={Status}&ProductLine={ProductLine}&Page={Page}&PageSize={PageSize}]
  Return List<DefectSummary>
  
  On error:
    Log error with timestamp
    Raise exception with user-friendly message
```

**Known Issue — Response Format:**
The backend may return the defect list wrapped in a JSON object (e.g., `{ "defects": [...] }`) instead of a bare JSON array (`[...]`). 

**Symptom:** If the table displays only the first row correctly and remaining rows show empty/zero values, the response is wrapped.

**Troubleshooting:**
1. Before implementing, call `GET /defects` directly in Postman and inspect the raw response body
2. If wrapped, create a wrapper structure (e.g., `ListDefectsResponse` with a `Defects` attribute of type `DefectSummary List`)
3. Update the `ListDefects` server action output parameter to use the wrapper structure instead of bare list
4. Update the table binding to reference the wrapped collection

#### 6.4.2 Form Actions

**Save button:**
- Validates all fields client-side first
- If validation passes, calls POST `/defects` with request body:
  ```json
  {
    "DefectId": "{input value}",
    "Status": {integer value from dropdown},
    "Severity": "{input value}",
    "ProductLine": "{input value}",
    "Description": "{input value}",
    "ReportedBy": "{input value}"
  }
  ```
- Shows loading spinner while request is in flight
- On success (HTTP 200, non-empty response):
  - Show success toast: `"Defect created successfully."`
  - Redirect to `DefectDetail?DefectId={newly created DefectId}`
- On conflict (HTTP 200, empty DefectId in response):
  - Show inline error: `"A defect with ID '{DefectId}' already exists. Please use a unique ID."`
  - Keep form visible for retry (user can edit DefectId field)
- On other error (HTTP 500, network error):
  - Show inline error: `"Failed to create defect. {error detail}"`
  - Keep form visible for retry

**Critical Implementation Note — Empty Body Conflict Detection:**
The backend returns HTTP 200 with an empty response body on duplicate DefectId instead of HTTP 409. Without explicitly checking whether the returned `DefectId` field is non-empty, the action silently completes and the user sees nothing. 

**Required Pattern:**
```
Response = POST /defects
IF Response.DefectId <> "" AND Response.DefectId <> null THEN
  Success path: Navigate to DefectDetail
ELSE
  Error path: Show "A defect with this ID already exists"
END IF
```

**Recommended Improvement:**
Replace the Status and Severity plain text/number inputs with **Dropdowns**:
- **Status dropdown:** Bound to the `DefectStatus` static entity (values: 1–5)
- **Severity dropdown:** Fixed list (Critical, High, Medium, Low)

This prevents invalid status codes and improves UX over free-text inputs.

**Cancel button:**
- Navigates back to DefectList without saving
- If form has unsaved changes, show confirmation: `"You have unsaved changes. Discard them?"`

#### 6.4.3 Form State Management

- **Unsaved changes warning:** If user navigates away with unsaved data, show confirmation
- **Disable submit during API call:** Prevent double-submission
- **Focus management:** Focus first invalid field after validation failure
- **Auto-save (optional):** Not recommended for this app; explicit Save button is safer

## 8. Data Conversion and Mapping

### 8.1 Status Integer Mapping (Critical)

The backend serializes Status as an integer (1–5). The UI must display human-readable labels.

**Pattern (use in all screens):**

```
IF Status = 1 THEN "Open"
ELSE IF Status = 2 THEN "Under Investigation"
ELSE IF Status = 3 THEN "Escalated"
ELSE IF Status = 4 THEN "Resolved"
ELSE IF Status = 5 THEN "Closed"
ELSE "Unknown"
END IF
```

**Better approach:** Use the `DefectStatus` static entity as a lookup:

```
GetLabelForStatus(statusInteger):
  Return DefectStatus.Find(Id = statusInteger).Label
```

### 8.2 DateTime Formatting

**Display format:** `YYYY-MM-DD HH:MM:SS` (or `YYYY-MM-DD` for dates only)

**Pattern:**

```
FormatDateTime(dateTimeValue, "yyyy-MM-dd HH:mm:ss")
```

**Timezone considerations:**
- All datetimes from the backend are assumed UTC
- Display in local browser timezone using ODC's built-in conversion (automatic on deserialization)
- If explicit control needed, use `DateTimeValue_ToLocalTime()` and `DateTimeValue_ToUTC()`

## 10. API Error Handling and Recovery

### 10.1 HTTP Status Code Handling

| Status | Scenario | UI Behavior | User Message |
|---|---|---|---|
| **200** | Success (any method) | Proceed to success flow | "Operation successful" (optional toast) |
| **200 (empty body)** | Not found (backend quirk; applies to GET /defects/{id}, POST /defects with duplicate) | Treat as not-found or conflict | "Defect not found" or "Defect ID already exists" |
| **401** | Invalid/missing X-API-Key | Redirect to Login screen | "Session expired. Please log in again." |
| **403** | Forbidden (role-based) | Show error, stay on screen | "You do not have permission to perform this action" |
| **404** | Not found (if backend maps to 404 in future) | Show error, offer back button | "Defect not found or has been deleted" |
| **409** | Conflict (duplicate key) | Treat response as 200 with empty body | "A defect with this ID already exists" |
| **500** | Server error | Show error with retry option | "Server error. Please try again." |
| **Network error** | No connectivity or timeout | Show error with retry option | "Connection failed. Please check your internet and try again." |

### 10.2 Error Response Mapping

**Pattern for all API calls:**

```
TRY
  Response = CallAPI(...)
  
  IF Response.StatusCode = 401 THEN
    Redirect to Login
  ELSE IF Response.StatusCode = 200 OR 201 OR 204 THEN
    Process success (check for empty body if applicable)
  ELSE IF Response.StatusCode >= 400 AND < 500 THEN
    Show user error: {Response.Message}
  ELSE IF Response.StatusCode >= 500 THEN
    Show user error: "Server error. Please try again."
  END IF
  
CATCH exception
  Log exception details
  Show user error: "Connection failed. Please try again."
  Offer Retry button
END TRY
```

### 10.3 Retry Logic

- Provide explicit "Retry" button on all error states
- Do NOT auto-retry (let user decide)
- Log all API failures for debugging (include timestamp, URL, status, response)
- After 3 failed retries, suggest contacting support

### 10.4 Backend Gaps Workarounds

**Gap 1: GET /defects/{DefectId} returns HTTP 200 with empty body when not found**

```
Response = GetDefectDetail(DefectId)
IF Response != null AND Response.DefectId != "" AND Response.DefectId != null THEN
  Display defect
ELSE
  Display "Defect not found or has been deleted"
END IF
```

**Gap 2: POST /defects returns HTTP 200 with empty body on duplicate DefectId**

```
Response = CreateDefect(...)
IF Response != null AND Response.DefectId != "" AND Response.DefectId != null THEN
  Redirect to DefectDetail
ELSE
  Display "A defect with this ID already exists"
END IF
```

## 13. Performance Considerations

### 13.1 Pagination and List Sizing

- **Default page size:** 20 records (balance between load time and user convenience)
- **Max page size:** 100 records (to prevent loading thousands of records)
- **Lazy loading:** Not required; pagination is sufficient
- **Infinite scroll:** Not recommended for manufacturing context; explicit pagination is clearer

### 13.2 API Call Optimization

- **No duplicate calls:** Use caching (in-memory or local storage) for small, static lookups (DefectStatus, severity values)
- **Refresh explicitly:** Don't auto-refresh list while user is on detail page; user clicks "Refresh" to refetch
- **Parallel loading:** On DefectDetail, fetch detail and history in parallel (two async API calls), not sequentially

### 13.3 Filter Debouncing

- **Text input filters:** Debounce by 300–500ms before triggering API call (prevents excessive requests while user types)
- **Dropdown filters:** Apply immediately (no debounce needed)
